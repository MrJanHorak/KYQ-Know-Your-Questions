# Instructor accounts and teams

The initial account flow is available at `/instructor`. It uses a named Firebase client app so that instructor sign-in does not replace a participant's anonymous or board-specific identity. After email verification, a server endpoint verifies the instructor's ID token and transactionally creates an instructor record, a personal team, and an owner membership. Repeated requests return the existing team. Firestore's default-deny rules prevent direct client access to these records.

Team owners can create and manage team-owned boards from `/instructor`. An owner can invite another verified account to share team ownership, revoke an invitation, or remove an owner. Ownership changes require password reauthentication and are recorded in the team's ownership activity. A team must retain at least one owner; inviting a second trusted owner is recommended. Owners can also invite a designated recovery contact using a one-time, seven-day link. The contact must accept using the invited verified account. The contact has no ordinary team access, but can grant themselves full team ownership at any time after password reauthentication; choose someone trusted to protect that account. Owners can revoke a pending invitation or remove the active contact. A replacement takes effect only after acceptance. The recovery action and contact changes are recorded in ownership activity. Owners select the team they want to manage. Owners and board admins can also create one-time, seven-day board invitation links for a verified email, and change or revoke existing managers. Board invitations are scoped to one board and do not grant team ownership. Share invitation links directly. Management requests check current membership and instructor identity on the server. The shared-password login has been removed. Unassigned boards remain inaccessible; migration is out of scope.

## Remaining work

1. Configure a general-purpose email provider and implement notifications to owners about ownership and recovery-contact changes. Ownership activity is visible in the app; email notifications are not yet sent. There is no recovery path when all owners and the recovery contact lose access.
2. Add operational safeguards for production: multifactor authentication, monitoring, abuse controls, account recovery, data retention, pagination for shared boards and manager lists, and cost/load testing for expected usage. Review Firebase Authentication and Firestore limits and deployment configuration.

The application has an authenticator-app enrollment and sign-in flow, including a second-factor challenge when reauthenticating to change ownership. It is hidden by default. To evaluate it, first upgrade a non-production Firebase project to Authentication with Identity Platform, enable TOTP MFA in that project, then build with `NEXT_PUBLIC_TOTP_MFA_ENABLED=true`. Firebase's Auth emulator does not support TOTP, so verify enrollment, sign-in, reauthentication, invalid codes and account recovery against the configured test project before production use.

To inspect a project's current MFA configuration without changing it, set `GOOGLE_APPLICATION_CREDENTIALS` to an authorized service account and run `node scripts/inspect-mfa-config.mjs PROJECT_ID`. This reports the MFA state and configured TOTP providers; it does not determine whether the project is eligible for an Identity Platform upgrade. Review [Firebase's upgrade and billing guidance](https://firebase.google.com/docs/auth) before changing a project.

MFA enforcement is off unless the server-managed Firestore document `_settings/security` contains the boolean `requireInstructorMfa: true`. When enabled, all instructor accounts—including board managers, owners and recovery contacts—must have signed in with a second factor to use instructor operations; ordinary board participants are unaffected. Previously issued instructor board sessions without MFA lose access. The account setup endpoint remains available to verified users so they can enroll. Users who enroll must sign out and sign back in with their authenticator before continuing. Deploy the app and Firestore rules before setting the document; leave the switch off until the TOTP flow, lost-authenticator recovery, and affected accounts have been validated in a test project. Enable the setup UI before enabling enforcement, or unenrolled users cannot enroll through the app. Restrict writes to the settings document to trusted operators; Firestore rules deny client access. If enforcement must be rolled back, set the field to `false` or remove the document. Enforcement does not prevent owners from independently unlocking a board as participants with its password.

The `teams`, `teams/{teamId}/members`, `boards/{boardId}/admins`, `instructors`, `teamInvitations`, and `boardInvitations` records are server-managed. Team owners have equal authority and only owners create boards. Board roles are cumulative: responder (reply and change status), moderator (also delete questions and replies), manager (also change passwords and export), and admin (also edit questions, manage board memberships and delete the board). Board admins can grant any board role, including admin, but cannot grant team ownership. Instructor-created board sessions check current membership so removing access also closes an existing session; participants who independently know the board password may still use participant access.

`scripts/test-instructor-boards.mjs` checks team isolation using the Auth and Firestore emulators. First build with `NEXT_PUBLIC_FIREBASE_PROJECT_ID=demo-kyq`, then run `firebase emulators:exec --project demo-kyq --only auth,firestore "node scripts/test-instructor-boards.mjs"`. It refuses to run without both emulator hosts. Run the rules checks with `firebase emulators:exec --project demo-kyq --only firestore "node scripts/test-board-rules.mjs"`. Rebuild with the normal project configuration afterwards. The current Firebase CLI requires Java 21 or newer.
